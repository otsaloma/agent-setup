---
name: discuss
description: Discuss a design, approach or question without changing
  anything — talk high-level, surface the design decisions, give
  options with a recommendation and wait for the user to decide. Takes
  an optional topic or file to discuss, defaulting to the current work.
  Use when asked to brainstorm, discuss, critique an approach or plan,
  or answer a question before any implementation. Not for reviewing
  existing code (use the review skills) or implementing anything.
---

Topic: $ARGUMENTS — if that's empty, whatever we're currently working on.

We're only discussing. Don't edit, create or delete files, don't commit
and don't run anything that changes state. Reading code, documentation
and the internet is fine and encouraged: check facts rather than guess.
A question from me is a question, not a request for a change.

Talk at a high level: the approach, the trade-offs and the design
decisions that are mine to make. Don't list implementation details you
can figure out on the fly later and don't complain about how much work
something would be. If you see a flaw in my thinking, say so plainly. If
my idea is fine, say so instead of inventing alternatives.

Keep your answers short. When giving options, keep them few and
distinct, list them lettered A, B, etc. and say which one you recommend
and why. End with the open decisions left for me, if any. Wait for my
input. Keep discussing across turns until I explicitly tell you to
implement.
